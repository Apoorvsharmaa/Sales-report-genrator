# Sales Report Generator

A small, dependency-free Python command-line application that reads a CSV file of
sales line items and produces a revenue report (JSON or plain text).

> **This repository is a deliberate test target.** The code contains intentionally
> planted bugs so that an automated bug-fixing agent can be evaluated against it.
> The ground truth is in [`BUGS.md`](BUGS.md). Everything else in this README
> describes the **intended (correct) behaviour** of the application.

---

## 1. Purpose

Small shops and sales teams often export orders as a spreadsheet. This tool answers
the common questions about such an export in one command:

- How much revenue did we make, from how many orders?
- What is the average order value?
- Which regions and which months brought in the most money?
- Which products earned the most?
- Which rows in the file were bad, and why were they ignored?

**Input:** one CSV file → **Output:** one report (JSON or text) on screen or in a file.

## 3. Architecture

The program is a straight pipeline. Each module has one job and only talks to the
next one through plain Python objects.

```
 CSV file
    │
    ▼
 loader.load_sales()          → (list[Sale], list[SkippedRow])
    │   validates each row; bad rows are skipped with a reason, never fatal
    ▼
 calculator.filter_by_date()  → list[Sale] within [start, end]
    │
    ▼
 calculator.*                 → totals, per-region, per-month, top products, AOV
    │
    ▼
 report.build_report()        → dict (money as strings, e.g. "12.50")
    │
    ▼
 report.render_json() / render_text()  → string
    │
    ▼
 cli.main()                   → stdout or --output file, exit code
```

Key design decisions:

| Decision | Why |
|---|---|
| Money uses `decimal.Decimal`, never `float` | Avoids binary floating-point errors such as `0.1 + 0.2 != 0.3`. |
| Each line total is rounded to cents (ROUND_HALF_UP) and then summed | Every figure in the report adds up exactly. |
| Money is written as strings in JSON (`"12.50"`) | JSON numbers are floats in most tools; strings keep the exact value. |
| Bad rows are skipped, not fatal | One typo in a 10,000-row export should not stop the report. Each skip is listed with its CSV line number. |
| Only file-level problems stop the program | Missing file, empty file, missing required column → exit code 2. |

## 6. Input format

A CSV file with a header row. Column order does not matter; surrounding spaces in
header names and a UTF-8 byte-order mark (common in Excel exports) are tolerated.

| Column | Required | Type | Rules |
|---|---|---|---|
| `order_id` | yes | text | Must not be empty. **One order may span several rows** (one row per product). |
| `date` | yes | `YYYY-MM-DD` | Must be a real calendar date (`2026-02-30` is invalid). |
| `region` | yes | text | Case and extra spaces are ignored: `north`, `NORTH`, ` North ` all mean **North**. |
| `product` | yes | text | Must not be empty. |
| `quantity` | yes | whole number | Must be **greater than zero**. |
| `unit_price` | yes | decimal | Must be a finite number ≥ 0 (`N/A`, `NaN`, `-5` are invalid). |
| `discount_pct` | no | decimal | Percentage 0–100. Blank or missing column means 0. |

Example (`data/sample_sales.csv`, first lines):

```csv
order_id,date,region,product,quantity,unit_price,discount_pct
1001,2026-01-05,North,Mechanical Keyboard,2,89.00,0
1001,2026-01-05,North,USB-C Cable,10,2.50,0
1002,2026-01-12,south,Laptop Stand,1,49.99,10
```

### Row validation

Any row that breaks a rule above is **skipped** and reported in `skipped_rows` with its
CSV line number (the header is line 1) and a reason. The rest of the file is still
processed. The program never crashes because of a bad value in a row.

### File-level errors (exit code 2)

| Situation | Message on stderr |
|---|---|
| File does not exist / cannot be opened | `Error: [Errno 2] No such file or directory: ...` |
| File is completely empty | `Error: input file is empty: ...` |
| A required column is missing | `Error: missing required column(s): unit_price, ...` |

## 7. Calculations

| Figure | Definition |
|---|---|
| Line total | `quantity × unit_price × (100 − discount_pct) / 100`, rounded to cents with **ROUND_HALF_UP** (`6.375 → 6.38`, `34.99125 → 34.99`). |
| Total revenue | Sum of the rounded line totals. |
| Order count | Number of **distinct** `order_id` values. |
| Line item count | Number of valid rows. |
| Units sold | Sum of `quantity`. |
| Average order value (AOV) | Total revenue ÷ **order count** (not ÷ line items), rounded to cents. `0.00` when there are no orders. |
| Revenue by region | Sum of line totals per normalised region, sorted A→Z. |
| Revenue by month | Sum of line totals per `YYYY-MM`, sorted chronologically. |
| Top products | The N products with the **highest revenue** (not units). Ties are broken A→Z by product name. |
| Date filter | `--start-date` and `--end-date` are **both inclusive**. Either may be omitted. |

## 8. Running the application

```bash
# JSON report to the screen (default: top 3 products)
python3 -m sales_report data/sample_sales.csv

# Plain-text report
python3 -m sales_report data/sample_sales.csv --format text

# Top 5 products, saved to a file
python3 -m sales_report data/sample_sales.csv --top 5 --output output/report.json

# Only Q1 2026 (both dates included)
python3 -m sales_report data/sample_sales.csv --start-date 2026-01-01 --end-date 2026-03-31

# Messy input: bad values should be skipped, not crash
python3 -m sales_report data/messy_sales.csv

# Help
python3 -m sales_report --help
```

> `--output` does not create folders. Run `mkdir output` first if you use `output/...`
> (the `output/` folder is git-ignored).

### Command-line options

| Option | Default | Meaning |
|---|---|---|
| `input` (positional) | — | Path to the CSV file. |
| `-o`, `--output PATH` | stdout | Write the report to a file. A confirmation line goes to stderr. |
| `-f`, `--format {json,text}` | `json` | Output format. |
| `--top N` | `3` | Number of top products. Must be ≥ 1. |
| `--start-date YYYY-MM-DD` | none | Keep sales on or after this date. |
| `--end-date YYYY-MM-DD` | none | Keep sales on or before this date. |

### Exit codes

| Code | Meaning |
|---|---|
| `0` | Report produced (even if some rows were skipped, or no rows matched). |
| `2` | Invalid arguments (bad date, `--top 0`, start after end) or unusable input file. Message on stderr, **no Python traceback**. |

## 10. Expected behaviour and how to check it

The files in `expected_output/` were generated by the **bug-free reference
implementation**. They are what the program *should* print:

| Command | Expected output file |
|---|---|
| `python3 -m sales_report data/sample_sales.csv --top 3` | `expected_output/sample_report.json` |
| `python3 -m sales_report data/sample_sales.csv --top 3 --format text` | `expected_output/sample_report.txt` |
| `python3 -m sales_report data/sample_sales.csv --start-date 2026-01-01 --end-date 2026-03-31` | `expected_output/q1_report.json` |
| `python3 -m sales_report data/messy_sales.csv` | `expected_output/messy_report.json` |

Quick manual comparison (macOS/Linux):

```bash
mkdir -p output
python3 -m sales_report data/sample_sales.csv --format text > output/actual.txt
diff expected_output/sample_report.txt output/actual.txt && echo "MATCH"
```

```bash
# Built-in runner (no installs needed)
python3 -m unittest discover -s tests -t . -v

# Or, if you installed pytest
python3 -m pytest -v

# One file / one test
python3 -m unittest tests.test_calculator -v
python3 -m unittest tests.test_loader.InvalidRowsAreSkippedTest.test_zero_quantity_is_skipped -v
```

The tests describe the **intended** behaviour. Because of the planted bugs, the
suite currently reports:

```
Ran 54 tests
FAILED (failures=15, errors=5)
```

(`failures` counts each failing sub-case separately.) When every bug is fixed
correctly, all 54 tests pass and every command in section 10 matches its expected
output file exactly. Test names describe behaviour only; the mapping from bugs to
tests is in `BUGS.md`.

## 12. Using this repository to evaluate a bug-fixing agent

1. Give the agent the repository **without `BUGS.md`** (e.g. copy the folder and delete it,
   or use a branch that doesn't contain it). The README, tests and expected outputs are
   fair game — they describe the specification.
2. Let the agent analyse, fix and re-run the tests.
3. Score its fixes against `BUGS.md`: which bug IDs it found, whether the root cause was
   fixed (not just the symptom), and whether all 54 tests pass with no test edits.

Suggested rule for the agent: *fix the application code only; do not modify files in
`tests/`, `data/` or `expected_output/`.*
